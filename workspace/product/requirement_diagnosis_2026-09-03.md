## 2. 技术可行性分析

### 2.1 文字定位（PaddleOCR）— 可行 ✅
- PaddleOCR 支持中英文混合识别
- 返回文字内容、bounding box、置信度
- 风险：手写体/艺术字体识别率可能低
- 降级方案：Tesseract OCR（但效果差）

### 2.2 样式还原（核心难点）— 部分可行 ⚠️
- **字体识别**：无通用方案，采用"特征向量近似匹配"
  - 提取笔画宽度、衬线检测、宽高比等特征
  - 与本地字体库做余弦相似度匹配
  - 妥协：接受"视觉接近"而非"精确匹配"
- **字号估算**：bbox 高度反推，可行 ✅
- **颜色提取**：K-means 聚类，可行 ✅
- **粗细/字重**：笔画宽度分析，可行 ⚠️（需调优）
- **对齐方式**：x 坐标序列分析，可行 ✅
- **位置/旋转**：OCR 直接返回，精确可用 ✅

### 2.3 原文字擦除 — 部分可行 ⚠️
- 简单背景（纯色/渐变）：OpenCV inpaint 可处理
- 复杂背景（UI/纹理）：需要 LaMa，MVP 阶段预留接口
- 风险：复杂背景修复效果可能不理想

### 2.4 技术栈验证
- Tauri + React + TS：成熟方案 ✅
- PaddleOCR：Python 封装，FastAPI 服务化 ✅
- OpenCV + Pillow：本地运行，无依赖 ✅
- macOS Apple Silicon：PaddleOCR 支持 MPS 加速 ✅

## 5. 关键技术方案

### 5.1 字体匹配方案

```
原文字图片区域
    ↓ 二值化（OTSU 自适应阈值）
    ↓ 提取笔画区域
    ↓ 计算特征向量：
    │  • 笔画平均宽度 (stroke_width)
    │  • 衬线有无 (serif_score)
    │  • x-height / cap-height 比值
    │  • 字宽宽高比
    │  • 笔画端点形状 (round/square/flat)
    ↓ 与本地字体库特征向量做余弦相似度
    ↓ Top-1 匹配（相似度 > 0.85）
    ↓ 如果 < 0.85 → 降级到最近似字体 + 提示用户
```

**字体库来源**：macOS 系统字体 + Google Noto 系列 + 思源系列

### 5.2 颜色提取方案

```
原文字区域 → 灰度 → OTSU二值化 → 文字mask
    ↓
原图 × 文字mask → 提取文字像素
    ↓
K-means (k=3) → 聚类中心 = 主色
    ↓
如果颜色差异小 → 单色；差异大 → 渐变色标记（V2 处理）
```

### 5.3 背景修复策略分级

| 背景类型 | 检测方法 | 修复方案 | 质量预期 |
|---------|---------|---------|---------|
| 纯色 | 颜色方差 < 阈值 | 直接填充 | ★★★★★ |
| 简单渐变 | 颜色方差中等 | 双线性插值填充 | ★★★★☆ |
| 简单纹理 | 纹理重复性高 | 纹理合成 | ★★★☆☆ |
| 复杂UI | 以上都不满足 | 预留 LaMa 接口 | ★★☆☆☆ |

## 9. 对抗审查记录

### 自问3个边界场景：
1. **文字比原来长5倍？** → 自动缩小字号到最小可读值（8pt），截断 + 提示用户
2. **手写体？** → 字体匹配失效，使用最近似字体 + 颜色/字号仍准确匹配
3. **FastAPI 启动失败？** → 友好错误提示 + 自动重试 + 一键修复脚本

### 最可能被挑战的假设：
> "完全本地运行，不需要云端 API、API Key 或大模型"

**挑战**：PaddleOCR 纯 CPU 模式可能较慢（>5s），MPS 加速需要正确 PyTorch 版本
**回退**：提供 CPU 模式 fallback，明确告知速度差异
