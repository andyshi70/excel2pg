## 二、B — 选B三态语义测试对抗审查

zhenhai 新增4条测试在 `TextRenderingSemanticsTests.swift:170-228`，逐条攻击审查：

### B.1 testWidthFitsScaleDownWhenWider（②变宽→k<1）

**攻击点**：探针是否真正验证了"新文本宽于原文"？

**审计结论**：
- 原文 `v1.0`（窄），新文本 `v1.0.0-beta`（宽）
- `FontProbe.inkWidth("v1.0", helvetica, 48)` 和 `FontProbe.inkWidth("v1.0.0-beta", helvetica, 48)` 均有效
- guard 条件 `newInkW > origInkW` 确保前提成立（否则 Issue.record 短路）
- 断言 `scaleFactor < 1` 且 `fontSizeUsed < 48`：正确，k0 = origInkW/newInkW < 1 → k=k0, fs=48·k0<48

**结论：断言精准，无空转风险。PASS。**

### B.2 testWidthFitsNoScaleWhenEqualOrNarrower（①等宽/窄→k=1）

**攻击点**：是否真的测了"变窄"场景而非等宽？

**审计结论**：
- 原文 `v1.0.0-beta`（宽），新文本 `v1.0`（窄）
- guard `newInkW <= origInkW` 确保前提
- 断言 `scaleFactor == 1` 且 `fontSizeUsed == 48`：正确，k0>1 → k=1, fs=48

**结论：测了变窄场景，语义正确。PASS。**

### B.3 testNeverScaleUpEvenForSingleChar（③永不放大）

**攻击点（核心疑问）**：FontProbe 对单字符 "V" 是否返回 nil？若返回 nil，FitCalculator.guard 失败返回 nil → 测试 Issue.record("fit 返回 nil") 后 return → 测试"通过"但实际没测到逻辑。

**源码审计**：
- `FontProbe.inkWidth("V", helvetica, 48)` 调用链：
  1. `CTFontCreateWithName("Helvetica", 48, nil)` → Helvetica 存在，返回有效 CTFont ✓
  2. `NSAttributedString(string: "V", attributes: [kCTFont: font])` → 有效字符串 ✓
  3. `CTLineCreateWithAttributedString(...)` → 单字符产生有效 CTLine ✓
  4. `CTLineGetTypographicBounds(...)` → 返回 "V" 的 typographic width（约 30-35px）✓
- 返回值：**有效 CGFloat（> 0），非 nil**
- FitCalculator 内部：`natural = 30+`（V at 48px），`targetInkWidthPx = origInkW`（v1.21.1 at 48px ≈ 180px）
- k0 = 180/30+ ≈ 5+ → k0 ≥ 1 → k=1, fs=48
- 断言 scaleFactor==1 且 fontSizeUsed==48：**正确**

**结论：FontProbe 对单字符 "V" 返回有效值，测试真正执行了 FitCalculator 逻辑，非空转。PASS。**

### B.4 testTooLongClampsToMinScale（兜底钳制）

**攻击点**：
1. scaleFactor 与 fontSizeUsed/f0 是否不一致？是否是隐藏bug？
2. 断言 `fontSizeUsed == 48 * 0.5 == 24` 是否正确？

**源码审计**：
- 超长串 vs targetW=10px → `k0 = 10/natural`（natural ≈ 200+）≈ 0.05
- k = k0 = 0.05（k0 < 1 分支）
- `tooLong = (0.05 < 0.5) = true` → 进入钳制：`fs = 48 * 0.5 = 24`
- ** scaleFactor 保持 k0=0.05，fontSizeUsed=24**
- 断言：`tooLong == true` ✓，`fontSizeUsed == 24` ✓

**scaleFactor ≠ fontSizeUsed/f0 的语义分析**：
- scaleFactor 是"自然缩放比"（新文本相对于目标宽度的理论 k0）
- fontSizeUsed 是"实际应用字号"（受 minScale 钳制后的结果）
- 两者不同是**设计意图**，非 bug：
  - scaleFactor 暴露"文本有多超限"（用于上层判断/日志）
  - fontSizeUsed 是渲染实际使用的字号
  - 无消费者仅依赖 scaleFactor 计算字号（TextRenderer 用 fontSizeUsed）

**结论：断言正确，scaleFactor/fontSizeUsed 分离是合理设计。PASS。**

## 五、最可能漏测的场景（对抗自省）

### 5.1 FontProbe 返回 nil 时 FitCalculator 测试空转（低风险但真实）

**场景**：若系统未安装 Helvetica 字体，`FontProbe.inkWidth` 返回 nil → `FitCalculator.fit` 返回 nil → 测试 `Issue.record("fit 返回 nil")` 后 return → 测试"通过"但未验证任何逻辑。

**当前缓解**：macOS 预装 Helvetica，测试在本机通过。但在 CI/其他开发者机器上可能触发。

**建议**：测试套件加 `guard` 检查（已有 `Issue.record`），但当前行为是 fail-open（记录问题但不阻塞）。**非阻塞，但需知晓。**

### 5.2 scaleFactor/fontSizeUsed 不一致的消费者误用

**场景**：tooLong 场景下 `scaleFactor = 0.05` 但 `fontSizeUsed = 24`（f0·minScale）。若有消费者用 `scaleFactor * fontSizeUsed` 计算字号（错误用法），会得到 `1.2px`。

**当前审计**：TextRenderer 仅用 `fontSizeUsed`（line 58），不使用 scaleFactor 计算字号。RenderedText 暴露 scaleFactor 供上层日志/调试，非渲染路径。**当前无误用风险。**

### 5.3 FitCalculator 不处理 targetInkWidthPx ≤ 0

**场景**：若 `targetInkWidthPx = 0` 或负数，`k0 = 0/natural = 0` → k=0 → tooLong（0 < 0.5）→ fs=24。渲染字号 24 但目标宽为 0，语义矛盾。

**当前缓解**：`EditingWorkflow` 传入 `BlockPatchBuilder.originalInkWidth(block)` 作为 target，该值 ≥ 0（bbox 宽度/逐字框并集）。无已知路径传入 0。**低风险，但缺少防御性 guard。**

### 5.4 双约束估算法仅在 Helvetica 48px 下验证

**场景**：`testFontSizeNotInflatedByLooseBBoxHeight` 用 Helvetica 48px + 1.4x bbox inflation 验证。其他字体（Hermes、CJK）、其他字号（24px、72px）未覆盖。

**当前缓解**：算法为字体无关的线性缩放（fontSize0 = height/1.15, fsWidth = 100*(widthAnchor/wideProbe)），理论上与字体无关。但**宽高比极端的字体**（如极窄/极宽）可能使双约束收敛到不同结果。**需知晓，非阻塞。**

### 5.5 真实 Hermes 字体未安装

**场景**：所有测试以 Helvetica 代理 Hermes。Hermes 实装后字形宽高比可能不同，影响 SizeEstimator 锚定值。

**当前状态**：已知风险（文档 Part E/F.4 已注明）。**非阻塞，但 Hermes 实装后需回归。**
