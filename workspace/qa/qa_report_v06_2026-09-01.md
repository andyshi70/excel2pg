## 二、对 3 个攻击点的判定（核心）

针对任务指定的 EditorState.select 重写逐点攻击：

### 攻击点 a：auto-confirm 分支是否真调 confirmEdit、分支条件是否完整 —— ✅ 通过

`EditorState.select(blockID:)`（EditorState.swift:135-177）：
- **liveSession 判定完整**：`.preview(pid == currentID)` **或** `workflow.hasPendingEdit(for: currentID)`（兜住 continueEditing 后已回 selected 但 pendingEdit 仍在的场景，:150-155）。
- **① confirmBlocked 拦截**：:157 命中碰撞/过长/样式未就绪 → setOverlay + return（不物化）。
- **② 草稿与已渲染预览比对**：:162-166 `previewResult.newText == trim(draft)`，与 `confirmPreview`（:207）同一判定，语义一致。
- **③ 真调 confirmEdit**：:168 `workflow.confirmEdit(blockID: currentID)` → Core 物化 + 入 undo 栈。非 mock 短路。

### 攻击点 b：阻塞拒绝分支是否不调 document.select（phase 保持）—— ✅ 通过

- :157-166 两条拒绝分支均 `return`，**先于** :174 `document.select(blockID)`，故 phase 不会被覆盖。
- 测试 `testBlockedPreviousBlockRejectsSwitchKeepingPreviewState` **真构造了碰撞**（白底图 + 邻块压住新 ink 区，断言 `confirmBlocked(A)` 落定）→ 点 B 后断言 selection 仍=A、phase 保持 `.preview(A)`、overlay 非空、B 未被触碰。四断言全绿，证明拒绝分支确实"保持现场"。
- **测试真实性核验**：全套走**真实 EditorWorkflow 管线**（真实 TextEraser/TextRenderer/pendingEdit），非 mock 跳过。不空转。

### 攻击点 c：有没有路径漏清理（previewResult/draft 残留）—— ⚠️ 发现一处潜在泄漏（低危）

**正常路径**（:174-176）：confirmEdit 成功后 `document.select(B)` → `clearEditingSession(currentID)`（清 draft/previewResult/feedback 三件套，:466-470）→ bump。完整。

**泄漏点**：:174 `guard document.select(blockID) else { return }`——若切块 select **失败**，A 已于 :168 物化（此刻 phase=idle），但 :175-176 的清理与 bump **被跳过** → 残留上一块 A 的 draft/previewResult，而 phase 已 idle（无选中）。UI 不刷新的同时残留脏会话。
- 可达性：`document.select` 失败仅发生在「块不存在」或 `phase == .loading`。confirm 后 phase=idle（非 loading），故仅「点击不存在块」可触发——真实 CanvasView 只点击 textBlocks 中真实块，**实际 UI 不可达**。定级低危、潜伏缺陷，建议后续补 `clearEditingSession` 兜底。

## 四、边界攻击（用户会怎么误用）

### 4.1 三块连续 A→B→C —— 逻辑正确，未直接测试（低危）
每步 `select` 对「当前块」auto-confirm：A 编辑→点 B（物化 A）、B 编辑→点 C（物化 B）。为测试 5 的复合叠加，`undoDepth` 递增。逻辑成立。

### 4.2 A 预览 in-flight 时点 B —— 逻辑拦截，无确定性时序测试（中低危，zhenhai 已如实标注）
`beginPreview` 置 phase=.preview(A) 且 :195 previewResult=nil；点 B 时 ② `guard let pr = previewResult` 失败 → 拒绝「预览尚未完成」。判定**逻辑正确**。但依赖异步时序（若预览已落定则走 auto-confirm 正常路径，若未落定则拦截），无专门的 `BlockingTextRenderer` 注入测试，仅由 `testContinueEditingThenSwitchRejectsWhenDraftStale` 间接覆盖同一拒绝分支。**风险可接受，但覆盖不完整**。

### 4.3 undo-during-preview 悬空态 —— 真可达，兜住了但 UX 困惑（中危，需关注）
- `document.undo()` **不改 phase**（EditorDocument.swift:146-152），故预览态 undo 后 phase 仍为 `.preview(A)`，pendingEdit 已清、previewResult/draft 仍残留。
- 工具条/顶部「撤销」按钮**无条件暴露**（ToolbarView:20、PxiuApp:62）→ **真实 UI 可达**（不只理论）。
- 再点 B：liveSession=true（preview 态）→ ① confirmBlocked=false → ② draft==previewResult 通过 → `confirmEdit` 抛 `noPendingEdit` → 捕获 → overlay「切换失败：没有待确认的预览」+ return。
- **判定：zenhai「安全兜底」结论成立**——不静默丢输入、不静默物化，拒绝并提示。但用户拿到的是晦涩错误文案且无法判断为何失败（需先重新预览），无测试守卫。**建议补用例 + 文案优化**（后者属 UI 层，报 zongguan 协调）。

### 4.4 同块重选（点自己）——**发现新问题：Ghost pendingEdit（高危点，最可能漏测）**
- **CanvasView:73-75 `.onTapGesture { state.select(blockID: block.id) }` 无任何当前块跳过守卫**——点击「当前选中块」也会进 `select`。zhenhai 注释称「通常对当前块点击不触发 select」，但代码层无此保护（BlockInteractor 也未拦）。
- 同块重选分支（:142-147）：`document.select(A)` 把 phase 从 `.preview(A)` 覆写回 `.selected(A)`，再 `clearEditingSession(A)` 清 draft/previewResult/feedback——**但 `workflow.pendingEdit` 不被清**（clearEditingSession 只管 UI 三件套，不清 Core 单槽）。
- **后果**：预览态点当前块 → 丢弃未确认会话，但 **pendingEdit 幽灵残留**。之后点 B：liveSession=`hasPendingEdit(A)`=true → ① 不阻塞 → ② draft=nil → `previewResult` 已 nil → 拒绝「预览尚未完成」→ **用户被迫重新预览 A 才能继续**。无数据丢失，但交互卡死式困惑。
- 同块丢弃会话本身是「旧语义保留」、非本次新增回归，但与 auto-confirm 交互形成新的困惑场景。**新增测试未覆盖**。
- 另一入口：OverlayViews「手动更换」（:56-58，低置信度块字体修复面板）也调 `state.select`，同机理。
