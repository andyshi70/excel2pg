## 三、对抗式攻击测试

### 3.1 改回原值仅 `phase==.preview` 时 cancelPreview — 残留分析

**攻击角度**: 非 preview 态（selected）改回原值只清 draft，是否留残？

**结论**: ✅ 无残留。selected 态下不存在活跃预览会话（previewResult==nil, pendingEdit==nil），仅清 draft 即完整。

**边界场景验证**: `testChangeBackToOriginalDuringPreviewClearsSessionAndNoConfirmFailure` 逐项断言：
- draft==nil ✅
- previewResult==nil ✅
- workflow.hasPendingEdit==false ✅
- phase==selected(A) ✅
- confirmPreview 不泄漏「预览尚未完成」或「没有待确认的预览」 ✅

### 3.2 confirmPreview draft==nil 分支 — 是否误伤真实内容路径

**攻击角度**: draft==nil 的 cancel 分支是否可能在用户正常确认时被触发

**结论**: ✅ 不会。真实内容变更必然有非 nil、非空 draft。`guard let draft, !draft.newText.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty` 仅拦截：(a) draft 被手动置 nil（异常时序）; (b) draft 内容全为空白。两条都是"无需物化"语义，cancel 是正确行为。

### 3.3 in-flight 判定 — 是否有无故禁用按钮场景

**攻击角度**: `phase==.preview && previewResult==nil` 是否在非预览阶段误判

**结论**: ✅ 不会。三条件必须同时满足：
1. phase 必须是 `.preview`（selected/idle/其他态排除）
2. 必须匹配当前块 ID（不同块排除）
3. previewResult 必须为 nil（预览已完成排除）

只有"正在预览、结果未到"状态命中。预览完成后 previewResult 有值，按钮即恢复可用。

### 3.4 第二入口「draft 死 preview 活」幽灵状态排查

对 EditorState 全部公开入口逐一审计：

| 入口 | 是否可能制造 ghost | 机制 | 风险 |
|------|-------------------|------|------|
| `select()` 同块重选 | ✅ 已修 | workflow.cancelPreview() + clearEditingSession | — |
| `select()` 切块 | ✅ 已修 | auto-confirm / 空会话检测 / 拒绝切换 | — |
| `handleTextInputChange` 改回原值 | ✅ 已修 | cancelPreview (preview态) / draft=nil (selected态) | — |
| `deleteBlock` | ✅ 安全 | clearEditingSession 在删除后调用 | — |
| `mergeBlocks` | ⚠️ **理论 ghost** | 仅清 draft+previewResult，**未调 workflow.cancelPreview()** | 见下方分析 |
| `undo()` / `redo()` | ✅ 安全 | workflow 内部处理 pendingEdit 清理 | — |
| `continueEditing` | ✅ by design | 保留 draft+pendingEdit 供续编 | — |
| `cancelPreview` | ✅ by design | 完整清理 | — |
| `open` | ✅ 安全 | 全量重置 draft/previewResult/viewport | — |

#### mergeBlocks 理论 Ghost（低风险）

**场景**: 用户在 preview 态编辑块 A → 此时通过命令行/其他 UI 触发 mergeBlocks(keep: A, absorb: B)

**影响**: draft=nil, previewResult=nil, 但 workflow.pendingEdit(A) 残留。后续用户切到块 C 时，select 的 auto-confirm 路径会对 A 执行 confirmEdit(pendingEdit)，用已清空的草稿文本确认——可能产生意料外的文本物化或 noPendingEdit 错误。

**实际风险**: **极低**。merge UI 仅在 `structuralActions` 中渲染，而 structuralActions 只在 `!isPreview` 时显示（InspectorView L51-53）。用户处于 preview 态时无法通过 GUI 触发 merge。**无需阻塞本次修复，建议后续补全 mergeBlocks 中的 cancelPreview 清理**。

## 五、最可能漏测的场景

### 5.1 mergeBlocks 在 preview 态的 ghost pendingEdit（理论，未覆盖）

如 3.4 节分析，mergeBlocks 未调 workflow.cancelPreview()。当前 GUI 不可达（preview 态不显示 merge 按钮），但若未来有其他入口（键盘快捷键、脚本）可在 preview 态触发 merge，则会制造 ghost 状态。**建议 P2 跟进**：mergeBlocks 开头加 `if case .preview = phase { cancelPreview() }` 防御。

### 5.2 快速连续 onChange 时序竞争（race condition）

用户极快速连续输入/删除字符（如键盘连按 delete），onChange 会密集触发 handleTextInputChange。当前实现依赖 Swift MainActor 串行化，理论上不会并发。但若未来引入后台线程编辑或 SwiftUI 响应批量化，可能出现：
- draft 被第二次 onChange 更新为新值
- 第一次 beginPreview 的 Task 仍在跑，使用旧 draft
- previewResult 落定时 newText 与当前 draft 不一致 → confirm 被拦截

**当前风险**: 极低（MainActor 串行 + beginPreview 内部有 `guard phase == .preview(blockID)` 检查）。**建议 P3 观察**。

### 5.3 文本框 onChange 与 CanvasView 点击切换的竞争

用户在 InspectorView 文本框改字的同时点击 CanvasView 上的另一个文字块。两个事件在同一 MainActor 迭代中处理的顺序取决于 SwiftUI 调度。若 onChange 先于 select 执行：
1. onChange 设 draft + beginPreview（phase→preview）
2. select 尝试切块 → liveSession=true → auto-confirm 或拦截

若 select 先于 onChange 执行：
1. select 切块（清前一块的 session）
2. onChange 对已非选中的旧块调 handleTextInputChange → guard 失败（block 不在选中态），不影响

**当前风险**: 低。两条路径都有保护。但建议 QA 在 GUI 冒烟时关注"改字同时切块"场景。

### 5.4 draft 全空格字符串

用户把文本框清空（或输入纯空格）。`confirmPreview` 的 draft guard 包含 `!draft.newText.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty` → 走取消路径而非报错。这是正确行为（不应确认空文本），但用户可能困惑"为什么点确认没反应"。**建议 P3 UX 优化**：提示"文字内容不能为空"而非静默返回。

### 5.5 undo 在 preview 态 → 继续编辑 → 再改字 → 确认

场景：选中 A → 改字 → preview 落定 → undo（清 pendingEdit，phase 仍 preview） → continueEditing（phase→selected，保留 draft） → 再改字 → preview → confirm。

当前 undo 后 phase 仍为 preview，continueEditing 将 phase 调为 selected，但 draft 和 previewResult 可能残留。此路径由 `testUndoDuringPreviewThenSwitchIsNotGhostBlocked` 间接覆盖（切块而非继续编辑），但**直接 continueEditing 后再改字确认的端到端路径未显式测试**。建议补充。
