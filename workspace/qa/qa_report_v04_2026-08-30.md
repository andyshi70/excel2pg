## 九、B CEO 验收复测 — FAIL

**验收项**：ch.jpg 版本区 `v0.20.1` → `v1.21.1` 真像素替换（导出图中）。

**结果**：**未通过**。

- 版本区域 `(592,717,569,156)` 最终内容与原始 ch.jpg 逐像素一致（diff 0，仅编码噪声）→ **v0.20.1 仍在版本区**。
- v1.21.1 全部像素（569×156 = 88764 像素）**完整、正立**出现在 `(592,407)` = 版本区 y 坐标的垂直镜像位置。
- 用户可见症状：预览层（叠加在正确位置）显示 v1.21.1 → 确认后版本区「什么都没变」，而 v1.21.1 像素出现在 Hermes 标题区内——预览与确认不一致，是用户最直接的失败观感。

**根因指向**（供 @dana / @zhenhai 定位）：
- `ImagePixels.rgba` 存在 `rgbaDirect` / `rgbaDraw` 双路径。ch.jpg 满足 rgbaDirect 全部条件（bpc=8、bpp=32、alphaInfo=noneSkipLast、byteOrderMask=0、colorSpace=nil、bytesPerRow=12032）。
- rgbaDirect 直拷 dataProvider 行序（未做 y 翻转/色彩管理），与 UI 图像坐标（CG 渲染 top-down、左上原点）相差垂直镜像。
- Core 内部自洽：`EditingWorkflowTests` 合成图（TestSupport.render 产出 premultipliedLast top-down RGBA）走同一自洽路径、同一坐标系内断言 → 全绿，**掩盖了镜像缺陷**。
- 镜像关系数学验证：`mirror_y = H − y − h = 1280 − 717 − 156 = 407`，铁证 sum=0 逐像素成立。

## 十、最可能漏测的场景（对抗审查）

1. **真实 JPEG / 不透明 alphaInfo / 无 colorSpace 图像的像素路径完全不在单测覆盖内**——EditingWorkflowTests 全部使用合成 RGBA premultipliedLast top-down 图，正是镜像缺陷的盲区。**本次失败 = 真实 JPEG 首次进入全链路**。
2. **rgbaDraw 路径**（非 rgbaDirect 条件的图）行序相反方向的行为未测，修复直接路径后须回归验证。
3. **色彩管理**：helper（CGContext 绘制 + 颜色管理）与 rgbaDirect（原始字节直拷）对同一 ch.jpg 的像素值系统性差异（meanAbs ≈ 276 量级）→ 物化结果在全图亮度/色域上可能仍有偏差，exported vs original 全图 diff 97.9%（meanAbs 6.8）包含再编码 + 区域大变 + 色彩路径三者叠加，需分开核验。
4. **预览与确认的一致性**：previewPatchLayer 用 top-left 语义定位 patch.after，与物化落点（镜像）不一致——修复后必须回归「预览所见 = 确认所得」。
5. **undo 视觉恢复**：修复坐标后需重测 undo 在显示坐标系把镜像区还原为原图（本次已验证 Core 自洽 OK，但那是镜像坐标系内）。
6. **超大图 / 非 4 字节对齐 bytesPerRow / 16bit / P3**：bytesPerRow ≠ width*4 的路径未覆盖。
7. **字形方向歧义**：本次正立 156/0 证明「补齐位置 = H−y−h 且字形不翻转」；若某路径同时翻转行序与镜像，可能出现「位置对但字形镜像」的隐性 bug，修复时须同时断言位置与方向。
